## [Unreleased]

## [1.7.1] - 2026-10-21

### Fixed
- **Signups failed on cached join pages with "That was quick…".** The form's signed timestamp (`ts`/`sig`) was only ever printed into the page HTML, so a full-page cache (Cloudflare APO here, serving `/register/` with an age of about 64 hours) handed every visitor a token past the 12-hour `FORM_TOKEN_MAX_AGE`, and reloading served the same stale copy. New public route `GET signup/token` returns a fresh token with `Cache-Control: no-store`; `passkeys-signup.js` fetches it on load and waits for it before posting, keeping the rendered token if the call fails. A submit that still comes back expired (a tab left open past 12 hours) fetches another token and retries once with the same Turnstile answer, which the server has not spent yet because it checks the form token first.
- **The error now says what happened.** `SignupService::form_token_problem()` reports `invalid`, `early` or `stale` (`verify_form_token()` wraps it). Too soon keeps `rtpk_signup_form` with "That was quick. Please wait a moment and try again."; forged, missing or stale tokens return `rtpk_signup_form_expired` with "This page has expired. Please reload it and try again."

### Tests
- `SignupServiceTest`: the new error codes and messages, `form_token_problem()` for each case. `SignupFlowIntegrationTest`: the token route (fresh, signed, `no-store`, 403 while signups are off) and a three-day-old token reported as expired. JS (`signup.test.mjs`): the fresh token replaces the rendered one, an expired token is refreshed and retried once with the same Turnstile answer, a second expiry shows the message instead of looping, a too-quick submit is not retried.

## [1.7.0] - 2026-10-19

### Added
- **My Garage.** Members keep the Rivians they drive on their account so the other RivianTrackr plugins can show what applies to them. New `Vehicles` class holds the shared vocabulary: models `r1t`, `r1s`, `r2` with their label (`R1T`, `R1S`, `R2`, as the Tire Guide's reviews and wheels write them), Software Updates platform (`r1`, `r2`, whose `gen1`/`gen2` slugs are reused as-is), Tire Guide filter group (`R1`, `R2`) and generations by model year (R1 `gen1` 2022–2024 and `gen2` 2025+, R2 `gen1` 2026+), extendable through `riviantrackr_garage_models` (R3 once it ships; malformed entries are dropped). Pickers offer years from a model's first to next year. New `Garage` class stores up to five vehicles in `riviantrackr_passkeys_garage` user meta: model, model year, generation (taken from the year when not chosen), an optional nickname and up to four wheel sets, each a Tire Guide wheel with one of its sizes or any wheel with the tire size typed in (metric, LT, Z-rated and flotation sizes, normalized), plus a label like "Winter". One vehicle is the default: the first one, or whichever is picked; removing it hands the default to the next. `Garage::for_user()` describes each vehicle with every plugin's vocabulary, its wheel sets and every tire size it wears; wheels from the guide are read fresh, so renames follow and a dropped size falls back to stock.
- **Garage tab** on the account page, after Profile: the list of vehicles (nickname or year and model, generation, a chip per wheel set with aftermarket ones outlined in violet, a Default badge, **Make default**, **Edit**, **Remove**) and a form with model, model year, generation (set from the year, changeable), nickname and wheel rows (factory wheels, then aftermarket, then "Another wheel" with tire size and name fields; up to four). An empty garage opens the form straight away. Field errors land on the right row (`wheels.1.size`). The Overview shows a Vehicles count, a "Your garage" quick link and, while the garage is empty, an **Add your Rivian** card. Selects on the account page get a drawn chevron.
- **Reading the garage from other plugins.** `apply_filters( 'riviantrackr_garage', null, $user_id )` returns the garage (or `null` when this plugin is inactive, an empty garage when signed out); `riviantrackr_garage_updated` fires after every change. Every front-end page gets `window.riviantrackrGarage` in the head (script handle `riviantrackr-garage`): `signedIn`, `vehicles`, `defaultId`, `garageUrl`, `joinUrl`, `signInUrl`, `maxVehicles`; the same for every visitor who is signed out, so cached pages stay correct. `riviantrackr_passkeys_garage_script` turns it off. The account page updates it and fires `riviantrackr:garage` on `document` after each change.
- **`[riviantrackr_garage_cta theme="dark|light"]`**: "Save your Rivian" with **Create a free account** (the join page, or core registration when open) and **Sign in** for visitors who are signed out; "Add your Rivian" linking to the Garage tab for members with an empty garage; nothing once a vehicle is saved. New `assets/passkeys-garage.css`, loaded only where the card renders. The signed-out account page adds "New here? Create a free account" when a join page is set.
- REST routes `GET account/garage`, `POST account/garage/vehicles`, `POST|DELETE account/garage/vehicles/{id}` and `POST account/garage/default` (writes 30/min per user; 409 when the garage is full).
- `TireGuide::wheels()` reads the guide's wheels (`RTG_Database::get_all_wheels()`, or `wp_rtg_wheels` on builds without it) as id, name, sizes (stock first), vehicles and whether it is aftermarket.
- Personal-data exporter and eraser for the garage, so "Request my data" includes it and erasure requests remove it.

### Changed
- The default tab list is `overview`, `profile`, `garage`, `security`, … The tabs filter contract is unchanged.
- Uninstall also removes the garage meta.
- `TireGuide` keeps its table checks in a static property with `forget_tables()`, so tests can look again.
- `.phpcs.xml` accepts the shared `riviantrackr_garage` hook prefix.

### Fixed
- The Profile tab's photo card sat flush against the Display name field; it now has the same gap as the other cards.

### Tests
- `VehiclesTest`: the built-in models and their slugs, generation by year, year ranges (open and retired), labels, the models filter and what it drops, the picker catalog. `GarageTest`: wheel normalization, validation (generation from the year or kept, model and year limits, nickname, guide wheels with stock or alternate sizes, typed sizes, blank rows, per-row errors, aftermarket wheels for another model, the four-set cap), tire sizes, add/update/remove/default, the five-vehicle cap, the updated action, tidying stored data, fresh guide wheels and fallbacks, the filter, the page data, the call-to-action states, privacy export and erase. `TireGuideTest`: wheels from the table fallback. `AccountPageTest`: the garage tab id. `GarageIntegrationTest` (real WordPress): sign-in required, add/edit/default/remove through REST, field errors, the filter, the printed script, the exporter and account deletion. JS (`garage.test.mjs`): the empty garage opens the form, years and generations follow model and year, wheel options follow the model, size picks and typed sizes, saving posts every wheel set and redraws (nudge, count, page-wide garage, event), server errors per row, the wheel row cap, editing, make default, remove, a full garage.

## [1.6.0] - 2026-10-19

### Added
- **Profile photos.** The account page's Profile tab opens with a **Your photo** card: the current avatar, **Upload a photo** (JPG, PNG, GIF or WebP, 2 MB by default via the new `riviantrackr_passkeys_avatar_max_bytes` filter, never below 100 KB) and **Remove photo**. New `Avatars` class: uploads are checked server-side (upload error, size, real MIME through `wp_check_filetype_and_ext()`, at least 64px each way), cropped to a centred square of at most 512px with the image editor (the editor's output path is used, since PHP temp names have no extension), stored through `media_handle_sideload()` as a private attachment owned by the member (members need no `upload_files`; the checks stand in for it), and pointed at by `riviantrackr_passkeys_avatar` user meta. `pre_get_avatar_data` serves the photo for every shape `get_avatar()` accepts (ID, email, `WP_User`, `WP_Post`, `WP_Comment`), so it shows in the account header, comments, author boxes and wp-admin; everyone else keeps Gravatar. A new upload deletes the previous attachment, Remove deletes it and falls back to Gravatar, and deleting the account takes it along with the member's other posts. New routes `POST account/avatar` (multipart field `avatar`, 10/hour per user) and `DELETE account/avatar`; `riviantrackr_passkeys_avatar_updated` action. The account script validates size and type before uploading, posts multipart with the REST nonce and swaps every avatar image on the page.

### Changed
- Uninstall also removes the avatar pointer meta (uploaded photos stay in the media library).

### Tests
- `AvatarsTest`: user resolution for every `get_avatar()` input, the filter's square/full fallback, validation of missing, failed, oversized, non-image, mislabelled and tiny uploads, the size filter's floor. `AvatarIntegrationTest` (real WordPress): a 640×480 sample becomes a 480×480 private attachment served by `get_avatar_url()` by ID, email and comment; a 1920×1080 replacement is cropped and scaled to 512×512 and the old attachment deleted; text files, mislabelled images, tiny images and signed-out requests are refused; removal returns to Gravatar; deleting the account deletes the photo. JS: local size/type checks, the multipart upload swapping every avatar image, and confirm-gated removal.

New routes `POST account/data/export` and `DELETE account` (`confirm`). New setting **Let members delete their own account** (default on). ## [1.4.0] - 2026-10-18

### Added

## [1.3.0] - 2026-10-18

### Changed
- **Favorites are now the tire guide's saved tires.** The account page's Favorites tab read the tire guide's retired `wp_rtg_favorites` table (the guide dropped favorites in 1.90.0 and stopped creating the table), so on a fresh site the tab never appeared, and on an older site it showed a stale list the guide's heart never wrote to. The tab lists size, "$289 today", "Saved Oct 3" and a green "▼ $12 since you saved it" (or a rise), links to the guide's page to compare, and its empty state says where the heart is. The overview stat, quick link, confirm prompt, REST messages, settings description, invitation email ("Save tires and leave or edit your tire reviews") and docs follow. The tab id, the `riviantrackr_passkeys_account_tabs` filter contract and the `DELETE account/favorites/{tire_id}` route are unchanged.

### Tests

## [1.1.0] - 2026-10-15

### Added
- **Custom login pages.** New `[riviantrackr_login theme="dark|light" redirect=""]` shortcode renders `wp_login_form()` in the plugin's card: passkey button first, "or", username, password, "Keep me signed in", "Sign in", "Lost your password?" and (while signups are allowed and a join page is set) "Create an account". It shows messages for `?login=failed`, `?login=empty`, `?loggedout=true`, `?checkemail=confirm`, `?rtpk_invite=expired` and `?rtpk_signup=exists`, the "sign in once with your password" hint when `redirect_to` leads to passkey setup, and "You're signed in as …" with a Continue link for signed-in visitors.
- **Settings → Passkeys → Pages:** pick a **Sign-in page** and a **Join page** (published pages only), **Send wp-login.php visitors to these pages** and **Brand the remaining wp-login.php screens**.
- **wp-login.php routing** (`LoginRouter`, when the redirect toggle is on and a sign-in page is set): `login_url` points at the sign-in page (keeping `redirect_to`; forced reauth stays on wp-login.php), `register_url` at the join page; GET requests for the login or register screen are redirected with `redirect_to`, `login`, `loggedout`, `checkemail`, `rtpk_invite` and `rtpk_signup` carried over; `wp_login_failed` and empty-credential `authenticate` results send the visitor back with `?login=failed|empty`. POST requests, `interim-login`, `reauth`, signed-in visitors and the `postpass`, `logout`, `lostpassword`, `retrievepassword`, `resetpass`, `rp`, `confirmaction`, `passkey-setup` and `passkey-signup` actions are never redirected. The decision is a pure `LoginRouter::resolve()` covered by tests.
- **wp-login.php skin** (`LoginBranding`, `assets/passkeys-wp-login.css`): dark `#121418` page, `#16191e` card, `#3a3e45` inputs and borders, warm-neutral text, gold `#fba919` primary with `#15130e` text, gold links and checkbox; the WordPress logo is replaced by the invitations logo → theme custom logo → site icon → site name, and the header links to the home page. `passkeys-setup.css` gains a `body.rtpk-branded` variant so the passkey setup and signup landing pages (and the manager/signup form embedded in them) match.

Requests go to `POST riviantrackr-passkeys/v1/signup/request`; **no WordPress user is created** until the visitor clicks the emailed link. Pending requests live in a new `wp_riviantrackr_pending_signups` table (SHA-256 of a 32-byte single-use token, hashed IP, configurable expiry, default 24 hours) and are purged as they expire.
- **Spam defences on signup:** hidden honeypot field, signed minimum-time check (3 s), 5 requests/hour per IP and 3/hour per address, a built-in list of ~170 disposable-email domains (subdomains included) plus an admin-editable list, and optional Cloudflare Turnstile (site/secret keys; verified server-side via `siteverify`, skipped when the keys are blank). The response is always "check your inbox"; an address that already has an account gets a sign-in reminder instead of a signup link, so nothing reveals who is registered.
- **Verification landing page** at `wp-login.php?action=passkey-signup&token=…`: creates the user (role from settings, never Administrator; random password; username derived from the email's local part and de-duplicated), fires `user_register`, signs the member in and redirects to the existing passkey setup page with the configured continue URL. Expired or used tokens show a friendly page with a "send me a new link" form.
- **Settings → Passkeys → Open signup:** allow toggle with pending-link count, role, link expiry, continue URL, Turnstile keys, extra blocked domains, verification email subject/message, admin notification toggle.
- **Hooks:** `riviantrackr_passkeys_signup_allowed` filter (`$allowed, $email, $input`), `riviantrackr_passkeys_signup_email` and `riviantrackr_passkeys_blocked_domains` filters; `riviantrackr_passkeys_signup_requested`, `_signup_verified` and `_signup_login` actions. Constants `RTPK_SIGNUP_IP_RATE_LIMIT`, `RTPK_SIGNUP_EMAIL_RATE_LIMIT`, `RTPK_SIGNUP_MIN_SECONDS`.
- **Passkey invitations.** New **Users → Passkey invitations** screen: see how many members have a passkey, filter by role and previous invitations, edit the email (plain text with `{name}`, `{site}`, `{link}`, `{expires}`, `{login_url}` placeholders, wrapped in a branded HTML template), send yourself a test, then send in batches of 20 with a live progress log. Only members without a passkey are ever emailed.
- **Users list integration.** A "Passkeys" column (count, or "Invited N ago"), a "Send passkey invite" row action, and a "Send passkey invitation" bulk action.
- **One-tap setup page** at `wp-login.php?action=passkey-setup`: a focused screen with the pitch, a single "Create a passkey" button, a "Continue" button on success and "Skip for now". Invitation links carry a single-use token (SHA-256 hash stored in user meta, expiry configurable, default 7 days). With "Link signs the member in" enabled (default), a valid token sets the auth cookie and opens setup directly — the same trust level as a password-reset email; otherwise, or once the token is spent, the normal login form shows a hint and redirects to setup after sign-in.
- **Hooks:** `riviantrackr_passkeys_invite_email` filter; `riviantrackr_passkeys_invite_sent` and `riviantrackr_passkeys_invite_login` actions.
- Settings → Passkeys links to the invitations screen.
- **Email branding.** The invitation is rendered in the site's dark "ink & brass" palette (deep `#121418` background, `#16191e` card, warm-neutral text, gold button with dark text) or a light variant, with your logo in the header (media-library picker; defaults to the theme's custom logo, then the site icon, then the site name). A **Preview** button renders the current draft inline, and **From name / From email** apply to invitation emails only (an SMTP plugin that forces a from address still wins).
- **Bulleted lists in the email.** Lines starting with `*` or `-` render as a gold-bulleted list; the default message now lists what signing in unlocks (commenting, tire favourites and reviews, new-article notifications).
- **Asset cache-busting.** Scripts and styles are now versioned with the file's modification time, so every deploy refreshes browser caches without a version bump.

### Changed
- Invitation, setup and signup links are built from `site_url( 'wp-login.php' )` instead of `wp_login_url()`, so they keep pointing at wp-login.php when `login_url` is filtered. `SetupPage::expired_hint()`, `SetupPage::setup_hint()` and `SignupPage::exists_hint()` expose the hint copy shared with the sign-in page.
- `ProfileManager::markup()` is now public and accepts title/description/button/setup overrides so other screens can embed the manager.
- `InviteService::render_branded()` and `InviteService::deliver()` expose the branded email template and from-address handling so other emails (signup verification) share them. Database schema version is now 2.
- Uninstall also removes the pending-signups table and the invitation/signup option rows (unless "Keep passkeys when the plugin is deleted" is on).

## [1.0.0] - 2026-10-15

### Added
- **Passkey (WebAuthn / FIDO2) sign-in.** "Sign in with a passkey" on `wp-login.php` and `wp_login_form()` forms, plus browser autofill (conditional UI) so saved passkeys appear in the username field. Successful logins set the normal auth cookie and fire `wp_login`.
- **Self-service passkey manager** on the WordPress profile screen (add, rename, remove) and via the `[riviantrackr_passkeys]` shortcode for front-end account pages (dark "ink & brass" theme, `theme="light"` available). Administrators can remove passkeys from other users' profiles.
- **Settings → Passkeys** screen: relying party name and ID, user-verification policy (preferred/required), additional allowed origins, prompt timeout, login button and autofill toggles, keep-data-on-uninstall.
- **REST API** under `riviantrackr-passkeys/v1`: `register/options`, `register/verify`, `login/options`, `login/verify`, `credentials`, `credentials/{id}` (rename, delete).
- **Security model:** single-use challenges that expire after five minutes, exact-origin matching on `clientDataJSON.origin` ahead of the library's suffix check, signature-counter regression detection for cloned authenticators, per-IP rate limits on login endpoints and per-user on registration, opaque 32-byte user handles, and a cap of 10 passkeys per account.
- **Hooks:** `riviantrackr_passkeys_pre_login` (deny with `false` or `WP_Error`), `riviantrackr_passkeys_allowed_origins`, `riviantrackr_passkeys_client_ip`; actions `riviantrackr_passkeys_registered`, `_login`, `_deleted`, `_counter_mismatch`.
- **Bundled `lbuchs/webauthn` v2.2** (MIT) under `lib/`, autoloaded by the plugin; no Composer required on the server.
- **Tooling:** PHPUnit suite with a software P-256 authenticator that drives real registration and assertion verification, `node:test` JS tests, PHPCS (WordPress standard), esbuild minification, and GitHub Actions CI on PHP 8.1–8.4.
